# Float parsing & DEFLATE (ufbx.c lines 1349-3280)

## Purpose
This region provides two independent, locale-independent, dependency-free numeric/byte-stream primitives that everything else in ufbx builds on: (1) a from-scratch `strtod`/`strtof` replacement (`ufbxi_parse_double`) used by the ASCII FBX parser to turn decimal-literal text into IEEE-754 doubles/floats with correctly-rounded results and no dependence on the C library or the process locale, and (2) a complete, allocation-free, streaming zlib/DEFLATE decompressor (`ufbx_inflate`) used to decompress the binary-FBX "compressed property" blocks (arrays compressed with zlib, used pervasively for vertex/index arrays in binary FBX ≥ 6100). Both are performance-sensitive hot paths (every float and every big array in a scene goes through them) so they are written with fast/slow-path splits, branchless bit-reader tricks, and precomputed lookup tables rather than naive reference implementations. Neither depends on any other ufbx subsystem; both are pure functions over byte buffers (inflate optionally streams via a caller callback).

## Key data structures

### Float parsing
- **`ufbxi_bigint`** (1357-1369): a growable arbitrary-precision unsigned integer as an array of 32-bit "limbs" (little-limb-endian, like GMP), with `capacity`/`length`. Backing storage is caller-provided fixed arrays (`mantissa_limbs[42]`, `divisor_limbs[42]`, `quotient_limbs[42]` in `ufbxi_parse_double`), so there is no heap allocation — sizes are bounded by construction (max 14 accumulated 18-digit "limb groups" via `max_limbs`, plus room for shifting).
- **`ufbxi_pow5_tab`** (1371-1376): table of 5^0..5^27 as `uint64_t`, the largest power of 5 that fits in 64 bits with room for multiply-accumulate. Used both to fold parsed decimal digit chunks into the bigint (mantissa scaling) and to build divisor/multiplier bigints for the decimal exponent.
- **`ufbxi_pow10_tab_f64`** (1378-1380): `1e0..1e22` as exact `double` literals — the fast path table (10^22 is the largest power of ten exactly representable in a double, and 2^53 is the largest exactly-representable integer mantissa).
- **`ufbxi_parse_double_flag`** (1531-1534): `ALLOW_FAST_PATH` (only enabled if the runtime's FP evaluation mode is verified to be round-to-nearest double, checked once via `ufbxi_parse_double_init_flags`, 1795-1805) and `AS_BINARY32` (parse as float instead of double, reusing the same bigint machinery with different mantissa/exponent bit widths).

### DEFLATE
- **`ufbxi_bit_stream`** (1890-1930): the streaming/bit-reader state. Fields of note: `input_left` (bytes not yet read from `read_fn`), `buffer`/`buffer_size` (either the user's scratch buffer or `local_buffer[256]`), `chunk_begin/chunk_ptr/chunk_yield/chunk_end/chunk_real_end` (a 5-pointer sliding-window scheme — `chunk_ptr` is the read cursor, `chunk_yield` is where progress-callback checks trigger, `chunk_end` is where a full 8-byte speculative read is still safe, `chunk_real_end` is the true end of valid bytes), `bits`/`left` (64-bit bit accumulator + valid-bit count), `progress_cb`/`cancel_bits`/`cancelled` (cooperative cancellation — see Quirks).
- **`ufbxi_huff_sym`** (`uint16_t`, packed symbol descriptor, documented exhaustively at 1932-1992). Bit layout: `[0:5]` total_bits (fast symbols) or extra_mask (non-fast); `[5]` END flag; `[6]` MATCH flag (lit/length tree only); `[7]` FAST flag (resolvable directly from the fast table); `[8:16]` a value field whose meaning depends on the other flags (literal byte / length-index / distance-index / code-length / long-table offset / code prefix). This packing lets the hot decode loop treat a symbol as a ready-to-use 64-bit shift amount (`total_bits`) without branching to check validity, because END is defined to never coexist with FAST.
- **`ufbxi_huff_tree`** (1997-2010): one canonical Huffman tree with three parallel decode paths:
  - `fast_sym[1<<fast_bits]` — direct lookup by the low `fast_bits` bits of the bit buffer (reversed-bit-order codes, since DEFLATE Huffman codes are packed MSB-first per RFC 1951 but consumed LSB-first from the stream).
  - `long_sym[UFBXI_HUFF_MAX_LONG_SYMS=380]` — a secondary flat table for codes between `fast_bits+1` and `fast_bits+UFBXI_HUFF_MAX_LONG_BITS` (5) bits, indexed via an offset stored in the `fast_sym` entry.
  - `sorted_to_sym[288]` + `past_max_code[16]` + `code_to_sorted[16]` — the fallback canonical-Huffman bit-by-bit decode (classic "sorted code list" scheme) for the rare codes longer than `fast_bits+5` bits.
  - `extra_shift_base[32]` / `extra_mask[32]` — per length/distance-index entry, packs the base value (upper 16 bits) and bit-shift amount (low 6 bits) needed to pull "extra bits" for that code out of the already-buffered 64-bit window, avoiding a second bit-consumption step.
  - `end_of_block_bits`: the reversed bit pattern of the end-of-block code, stashed for potential cancellation shortcuts.
- **`ufbxi_trees`** (2012-2021): a `{lit_length, dist}` pair plus the shared `fast_bits` used to build them (8 or 10, see Format details).
- **`ufbxi_inflate_retain_imp`** (2023-2028), mapped onto the public opaque `ufbx_inflate_retain` (1024 `uint64_t`s = 8KB): caches the *static* Huffman trees (RFC 1951 fixed codes) across multiple `ufbx_inflate` calls so repeated stored-block-less-often-used static blocks don't rebuild tables every call. `ufbx_static_assert` (2028) enforces it fits the public opaque buffer.
- **`ufbxi_deflate_context`** (2030-2037): per-call scratch — the bit stream, the chosen `fast_bits`, and the `{out_begin,out_ptr,out_end}` output cursor triple (single flat output buffer, no windowing needed since it's not a ring buffer — matches are always resolved against already-written output).

## Control flow / algorithms

### `ufbxi_parse_double` (1601-1793) — call order
1. Parse optional sign (1614-1616).
2. Digit loop (1617-1641): accumulate up to 18 decimal digits at a time into a `uint64_t digits`; once `num_digits>=18`, fold `digits` into `big_mantissa` via `ufbxi_bigint_mad(&big_mantissa, pow5_tab[num_digits]<<num_digits, digits)` (1625) — this multiplies the existing bigint by 10^18-ish (expressed as 5^n·2^n) and adds `digits`, i.e. classic "digit-chunking into a bignum." Digits beyond `max_limbs=14` chunks (i.e., beyond ~252 significant decimal digits) are *counted only* by adjusting `dec_exponent` (1631-1633) rather than stored — harmless since that many digits can't affect a double's value. `has_dot` tracks the decimal point to correctly bias `dec_exponent` (net effect: `dec_exponent` = position of decimal point relative to the last digit seen, negative for fractional digits).
3. Exponent suffix `[eE][+-]?digits` (1642-1661), clamped at `exp>=10000` to prevent overflow, folded into `dec_exponent`.
4. If the next character looks like `#/i/I/n/N`, delegate to `ufbxi_parse_inf_nan` (1663-1671, see below) and return early — no bigint math for special values.
5. **Fast path** (1677-1685): if allowed (`ALLOW_FAST_PATH`, only enabled when the runtime is verified round-to-nearest, see 1795-1805) and no bigint accumulation happened (`big_mantissa.length==0`, i.e. ≤18 digits) and `-22<=dec_exponent<=22` and the integer digit value fits in 53 bits, compute `digits / 10^k` or `digits * 10^k` directly in double arithmetic using the exact `ufbxi_pow10_tab_f64` table and return. This is the common case (short decimal literals) and avoids all bigint work.
6. Otherwise, materialize `big_mantissa` from the leftover `digits` if it wasn't already bigint-accumulated (1687-1695), or fold the final `digits` chunk in with one more `ufbxi_bigint_mad` (1692-1695).
7. Pick target format's bit widths: double = sign bit 63, 53 mantissa bits, exponent bias range ±1023; float (`AS_BINARY32`) = sign bit 31, 24 mantissa bits, ±127 (1697-1704).
8. **Negative decimal exponent** (dividing case, 1707-1756): 
   - Early underflow-to-zero check (1708): if `dec_exponent + mantissa_limb_count*10 <= -325` the value is guaranteed subnormal-underflow to 0.
   - Build a divisor bigint = 5^|dec_exponent| (using `ufbxi_pow5_tab` directly for the first ≤27 and `ufbxi_bigint_mul_pow5`, 1452-1458, chunking by 27 for the rest — the associated 2^|dec_exponent| factor is tracked purely in the binary `exponent`, not multiplied in, since dividing by 2^n is just an exponent shift).
   - **Small-value shortcut** (1717-1730): if the whole computation fits in two `uint64_t`s (`pow5==0` meaning ≤27 zeros needed, digits fit non-negative 63 bits), skip general bigint division and directly build 2-limb divisor / 4-limb mantissa (pre-shifted for precision) — this is the common "0.1", "3.14" case avoiding the general Knuth division below.
   - **General case** (1731-1754): build the divisor bigint via repeated `ufbxi_bigint_mul_pow5`, normalize it (shift left so its top bit is set — `ufbxi_bigint_shift_left`, 1460-1488), then shift the mantissa left enough bits (`mantissa_min_bits = divisor_bits + enc_mantissa_bits + 2`) to guarantee enough quotient precision plus one extra guard bit alignment trick (1749: nudge shift by 1 if it would leave the top mantissa bit exactly on a limb boundary, "so we can skip the first digit during division" — an optimization for the long-division routine).
   - Run **Knuth Algorithm D long division**, `ufbxi_bigint_div` (1404-1450) — a textbook multi-word division with `qhat`/`rhat` trial-quotient-digit refinement loop (1415-1420) and the standard "add-back" correction if the trial subtraction underflows (1430-1439). Returns `tail` = true if there was a nonzero remainder (needed for correct round-to-nearest-even later).
9. **Positive decimal exponent** (multiplying case, 1758-1763): overflow-to-infinity check (`dec_exponent + limbs*9 >= 310`), then `exponent += dec_exponent` and multiply the mantissa bigint by 5^dec_exponent via `ufbxi_bigint_mul_pow5` (the 2^dec_exponent factor again folds into the tracked binary `exponent`).
10. `ufbxi_bigint_extract_high` (1494-1514): pulls the top 64 significant bits out of the (possibly multi-limb) bigint result, normalizes (left-shifts so bit 63 is set, tracked via `p_exponent`), and sets `*p_tail` if any lower bits were nonzero (needed for round-to-nearest-even).
11. Final assembly (1765-1792): clamp/handle exponent overflow to ±infinity (1769-1770) and subnormal range by increasing `mantissa_shift` (1771-1774); round the 64-bit mantissa down to `enc_mantissa_bits` using `ufbxi_shift_right_round` (round-half-to-even, 1516-1529); reassemble sign/exponent/mantissa bit pattern and bit-cast to `double` or `float`.

`ufbxi_shift_right_round` (1516-1529) implements IEEE round-half-to-even: it looks at the bit that would be shifted out (`r_round`), whether the result would be odd (`r_odd`), and whether any nonzero bits were discarded either during this shift or earlier in the pipeline (`r_tail`, folding in the bigint-division remainder / bigint-extract tail flag) — rounds up only when exactly halfway *and* the result is currently odd, or when strictly more than halfway.

`ufbxi_parse_inf_nan` (1545-1599): recognizes (case-insensitively) `nan`, `nan(...)` (payload ignored), `inf`, `infinity`, and the legacy MSVC `1.#INF`/`1.#IND`/`1.#NAN` forms (1554-1568); returns a manually bit-constructed double (top 16 bits set directly, 1593-1597) rather than using `INFINITY`/`NAN` macros — again for determinism.

`ufbxi_parse_int64` (1807-1828) and `ufbxi_parse_uint32_radix` (1830-1846) are simple bespoke integer parsers (max 30 chars, decimal only for int64; decimal/hex for uint32) used elsewhere for FBX property/version parsing — trivial, no special algorithm.

### DEFLATE bit-reader plumbing
- `ufbxi_bit_stream_init` (2088-2139): sets up chunk pointers from the initial `ufbx_inflate_input` (`data`/`data_size`/`total_size`), computes `input_left` (bytes to be pulled later via `read_fn`), chooses `buffer` vs `local_buffer[256]`, and if the initial data chunk is under 64 bytes immediately calls `ufbxi_bit_chunk_refill` once to pad/merge. Also sets up the `progress_interval`/`chunk_yield` split so progress callbacks fire at roughly `progress_interval_hint` (default `0x4000`) byte granularity without checking on every single bit-refill.
- `ufbxi_bit_chunk_refill` (2051-2086): slides any left-over unconsumed bytes (`< 64`, `memmove`) to the front of `buffer`, pulls more bytes via `read_fn` if present, zero-pads the tail to a full 64 bytes (so the branchless 8-byte reads never read out of bounds), and resets the 5 chunk pointers.
- `ufbxi_bit_yield` (2141-2174): called when the read cursor passes `chunk_yield`; may trigger `ufbxi_bit_chunk_refill`, then (if a progress callback is registered) invokes it and handles `UFBX_PROGRESS_CANCEL` by force-switching the stream to point at a zeroed `local_buffer` (see Quirks — cancellation protocol) and recomputes the next `chunk_yield`.
- `ufbxi_bit_refill` (2176-2194) / macro `ufbxi_macro_bit_refill_fast` (2197-2202): the branchless bit-buffer refill (credited to Fabian Giesen's blog, "variant 4") — ORs in a raw 8-byte little-endian load shifted by the current valid-bit count, advances the byte pointer by `(63-left)>>3` bytes, and sets `left|=56`, guaranteeing 56-63 valid bits after each call without any branches. The macro variant is used in the hyper-hot fast inflate loop where the 8-byte read (`refill_bits`) is prefetched one iteration ahead.
- `ufbxi_bit_copy_bytes` (2205-2248): used for stored (uncompressed, BTYPE=00) blocks — drains any buffered whole bytes from `bits` first, then memcpy's straight from the current chunk, then (if the block spans past the current chunk) reads remaining bytes directly via `read_fn`, bypassing the bit buffer entirely.

### Huffman table construction — `ufbxi_huff_build` → `ufbxi_huff_build_imp` (2253-2472)
1. `ufbxi_huff_build` (2458-2472) computes `bits_counts[len]` = how many symbols have each code length (`bits_counts[0]` = unused symbols), then delegates to `_imp`.
2. `ufbxi_huff_build_imp` phase 1 (2287-2345) — canonical Huffman code assignment per RFC 1951 §3.2.2, generalized: iterate bit lengths 1..15, tracking `code` (first code at this length, doubled + previous count each step — standard canonical-code recurrence), `first_code[bits]`, `past_max_code[bits]` (one-past-last code, used by the slow decode path), and `total_syms[bits]` (cumulative symbol count up to this length, used to compute `sorted_to_sym` offsets). `num_codes_left` tracks whether the tree is exactly full; going negative is an **overfull** error (-1); ending nonzero when there's more than one symbol is **underfull** (-2, with a special-case allowance for the single-symbol tree, which canonically gets one 1-bit code, 2335-2339).
   - Within this same loop, for any bit length `> fast_bits` and `<= fast_bits + UFBXI_HUFF_MAX_LONG_BITS(5)`, it also pre-populates `fast_sym[]` entries (2309-2323) with **placeholder "long" redirect markers**: `mask = (1<<shift)-1` (shift=`bits-fast_bits`) and a `long_offset` that grows by `half_step=1<<(shift-1)` per distinct fast-table prefix — this reserves contiguous ranges of `long_sym[]` before the second pass assigns actual symbols into them. `last_valid_prefix` records where genuinely-long-and-covered-by-long-table codes end (beyond that, codes longer than `fast_bits+5` fall through to the slow sorted-list path).
3. Phase 2 (2354-2434): iterates every input symbol `i` with nonzero code length, in symbol-index order (not code order):
   - If `i` is a "match"/length/distance index requiring extra bits (`i >= sym_extra_offset`, table-provided extra info folded in from `ufbxi_deflate_length_lut`/`ufbxi_deflate_dist_lut`), and it needs a nonzero shift or lacks the END flag, allocate an `extra_shift_base[]`/`extra_mask[]` slot (`ix`) and repoint the symbol's value field at that slot instead of the literal value (2373-2378) — this indirection is what lets the decoder fetch base+extra-bits in O(1) via a table lookup instead of a switch.
   - Compute `sorted_to_sym[total_syms[bits-1]+index]` (canonical sorted-order slot) and the code's bit-reversed form `rev_code` (since codes are read LSB-first from the stream but assigned MSB-first canonically).
   - If `bits <= fast_bits`: fill **every** `fast_sym[]` slot whose low `bits` bits match `rev_code` (i.e. `hi_max = 2^(fast_bits-bits)` don't-care upper bits) with the fully-resolved FAST symbol (2390-2400).
   - Else if the code fits in the long table (`bits <= fast_bits+5` and within `last_valid_prefix`): resolve which reserved `long_sym[]` region the fast-table placeholder points to (walking the placeholder's low-order 1-bits to recover `long_bits`, 2404-2410) and fill the appropriate sub-range (2413-2420).
   - Else (very long code, only possible when `fast_bits<10`, since `fast_bits+5>=15` always covers max 15-bit DEFLATE codes when `fast_bits=10`): stash just a code-prefix redirect (`code>>(bits-fast_bits))<<8`) into `fast_sym[]` for the slow bit-by-bit path in `ufbxi_huff_decode_bits` to use (2421-2426).
   - Tracks the end-of-block (`i==256`) code's reversed bit pattern into `tree->end_of_block_bits` (2430-2433).
4. Regression-only assertions (`UFBX_REGRESSION`) verify every table slot got initialized exactly once — useful validation logic to port as unit tests but not runtime behavior.

### Symbol decode — `ufbxi_huff_decode_bits` (2474-2508)
1. Direct index `fast_sym[bits & fast_mask]`.
2. If FAST or END flag set, return immediately (O(1) common case).
3. Else if the symbol carries a nonzero `long_mask`, index into `long_sym[]` at `long_offset + (tail & long_mask)` and return (O(1) "medium-length code" case).
4. Else (rare, only for very long codes with small `fast_bits`), walk bit-by-bit: repeatedly shift one more bit from `tail` into `code`, increment `num_bits`, and check `code < past_max_code[num_bits]`; once true, resolve via `sorted_to_sym[code + code_to_sorted[num_bits]]`. This is the classic canonical-Huffman "compare against per-length max code" decode, needed only as a fallback.

### Dynamic Huffman table setup
- `ufbxi_init_dynamic_huff` (2604-2662): reads the 3-field DEFLATE dynamic-block header (`HLIT`+257, `HDIST`+1, `HCLEN`+4, packed 5/5/4 bits, 2616-2620), then reads `HCLEN` 3-bit code-length-code lengths in the fixed permutation order `ufbxi_deflate_code_length_permutation[]` (1867-1869, the RFC 1951 order `16,17,18,0,8,...`) into `code_lengths[0..18]` (2629-2637), builds a temporary 19-symbol "code length" Huffman tree (`huff_code_length`, fast_bits=`UFBXI_HUFF_CODELEN_FAST_BITS`=8) via `ufbxi_huff_build`, then calls `ufbxi_decode_dynamic_huff_bits` to expand that into the real lit/length+distance code-length array, then builds the two real trees (`trees->lit_length`, `trees->dist`) from slices of that combined array.
- `ufbxi_decode_dynamic_huff_bits` (2540-2602): drives the code-length alphabet decode loop per RFC 1951 §3.2.7: literal 0-15 = that code length (also remembered as `prev` for repeat codes); 16 = repeat previous length 3-6 times (2 extra bits); 17 = repeat zero-length 3-10 times (3 extra bits); 18 = repeat zero-length 11-138 times (7 extra bits). Bounds-checks that repeats don't overflow `num_symbols` (errors -18/-19/-20).

### Block decoding dispatch — `ufbx_inflate` (3131-3276)
1. Initialize bit stream and pick `fast_bits` (10 if `total_size>2048` else 8, unless `internal_fast_bits` override is given and validated to be 1..10 excluding 9, 3141-3147 — 9 is excluded because `UFBXI_HUFF_FAST_BITS` fast-path code assumes 8 or 10 specifically, see Format details).
2. Optional zlib header parse (3157-3167, skipped if `input->no_header`): validates `CMF&0xF==8` (DEFLATE method), `FLG&0x20==0` (no preset dictionary support), `(CMF<<8|FLG)%31==0` (header checksum), and `CMF>>4<=7` (window size ≤ 32K, i.e. valid `CINFO`).
3. Main block loop (3169-3253): reads 3-bit block header (`BFINAL` + 2-bit `BTYPE`); dispatches:
   - **BTYPE=00 (stored)**: byte-aligns the bit reader, reads `LEN`/`NLEN` (16 bits each) and validates `LEN == ~NLEN` (else -4), checks destination space, then uses `ufbxi_bit_copy_bytes` to stream the literal bytes directly (bypassing Huffman entirely).
   - **BTYPE=01 (static Huffman)**: lazily builds (once, cached in `retain`) the fixed RFC 1951 trees via `ufbxi_init_static_huff`.
   - **BTYPE=10 (dynamic Huffman)**: builds fresh trees per block via `ufbxi_init_dynamic_huff`.
   - **BTYPE=11**: reserved, error -7.
   - For BTYPE 01/10, an inner loop (3224-3240) repeatedly calls either `ufbxi_inflate_block_fast` (when `fast_bits==10` and there's enough headroom in both input (`UFBXI_INFLATE_FAST_MIN_IN`=8 bytes to `chunk_yield`) and output (`UFBXI_INFLATE_FAST_MIN_OUT`=2 bytes)) or `ufbxi_inflate_block_slow` (bounded to 32 symbols per call when the fast path *would* apply but doesn't fit right now, else unbounded) until the block's end-of-block symbol is hit (return 0) or a chunk/output boundary is reached (return 1, loop again) or a cancellation/error occurs.
4. After BFINAL, byte-align and read the trailing 4-byte big-endian Adler-32 checksum, verify against `ufbxi_adler32(dst, produced_size)` unless `no_checksum`.
5. Returns the number of decompressed bytes, or a negative error code (full catalogue documented at 3104-3130).

### `ufbxi_inflate_block_slow` (2805-2904) — generic decode loop
Per iteration: refill bits, decode `lit_length` symbol; if END, validate value==0 and return 0 (done); if plain literal (`!MATCH`), bounds-check output space and emit one byte; else it's a length code — extract `length` via the symbol's `extra_shift_base`/`extra_mask` entry pulled straight out of the *pre-shift* bit snapshot (`sym_bits`) using `ufbxi_wrap_shr64`, decode the `dist` symbol (error -11 if END), extract `distance` the same way, bounds-check (`distance` must not exceed bytes already written, `length` must fit remaining output space — else -12), then copy the back-reference. The copy uses a 16-byte-at-a-time `ufbxi_copy_16_bytes` fast path when there's ≥16 bytes of headroom and the match distance is ≥ effective chunk size (so overlapping short-distance copies, e.g. RLE-style single-byte-repeat matches, fall back to a byte-by-byte loop, 2887-2891, to get correct overlap semantics). Bounded by `max_symbols` so callers can interleave with fast-path checks/cancellation.

### `ufbxi_inflate_block_fast` (2911-3092) — the hot path
Heavily unrolled variant with hard preconditions (asserted, not checked): `fast_bits==10` exactly, at least 8 input bytes and 2 output bytes of headroom guaranteed by the caller for the whole call (loop only continues — `ufbxi_fast_inflate_should_continue`, 2943 — while both remain true, so within the loop body no per-byte bounds checks are needed for input). Speculatively decodes **two** lit_length-tree fast-table lookups per refill (`sym0`, `sym1`, macro at 2935-2941) since with fast_bits=10 up to two back-to-back single-bit-length codes plus overhead typically fit in the 56 available bits. Cases per iteration (2948-3037): both fast & both literal → emit 2 bytes and loop; both fast but sym0 literal/sym1 match → emit 1 literal, decode a distance symbol for sym1's match, fall through to copy; both fast and both flagged one way that resolves to a straight match+distance pair → fall through to copy directly; otherwise (sym0 not fast/is END, the "slow sym0" branches at 2996-3036) resolve sym0 via the long/slow path, handle END, handle plain-literal single-emit, or decode a dist symbol for a match. The final shared tail (3039-3081) computes `length`/`distance` from the extra tables exactly as the slow path does, prefetches the next 8 input bytes, bounds-checks the destination/source (bailing to error -12 if either would run out — note it does **not** fall back to the slow inflate function on ordinary end-of-buffer, it returns 1 to let the outer loop re-evaluate `fast_viable` and switch decoders), and performs the same 16-byte-chunked copy with short-distance byte-by-byte fallback as the slow path.

### `ufbxi_adler32` (2664-2803)
Standard Adler-32 (mod 65521, `a` init 1, `b` init 0) with three implementation tiers selected at compile time: SSE2 8-lane `__m128i` vectorized version (2686-2745, processes up to 5803-byte chunks aligned to 256 bytes using widening multiply-adds and a classic "sum of sums" trick to accumulate `b` without repeated wraparound), a portable 64-bit little-endian bit-trick version (2747-2790, processes 16 bytes/iteration by splitting bytes into two 32-bit-lane accumulators via masking, staying below overflow for up to `5552`/`380368439` bytes-worth of terms before requiring a mod), and a trivial scalar byte loop (2793-2796) for alignment padding and any remaining leftover/big-endian fallback. All three funnel into the same final `a %= 65521; b %= 65521;` and pack the result as `(b<<16)|a`.

## Format details
- **zlib stream header** (RFC 1950, checked at 3157-3167 unless `no_header`): 2 bytes, `CMF` then `FLG`. `CMF & 0xF` must be 8 (DEFLATE); `CMF >> 4` (CINFO, log2(window)-8) must be ≤7 (window ≤ 32768, else error -30 "Bad window size"); `FLG & 0x20` (FDICT) must be 0 — preset dictionaries unsupported (-2); `(CMF*256+FLG) % 31 == 0` is the mandated header checksum (-3 if violated).
- **DEFLATE block header** (RFC 1951 §3.2.3): 3 bits per block — bit 0 = BFINAL, bits 1-2 = BTYPE (00 stored, 01 fixed Huffman, 10 dynamic Huffman, 11 reserved/error).
- **Stored block** (BTYPE=00): after byte-align, 2×16-bit fields `LEN` then one's-complement `NLEN`; must satisfy `LEN == ~NLEN & 0xFFFF` (error -4 otherwise); raw bytes follow.
- **Fixed Huffman code lengths** (RFC 1951 §3.2.6, hardcoded at 2522-2527): literal/length symbols 0-143 → 8 bits, 144-255 → 9 bits, 256-279 (includes end-of-block=256 and length codes 257-279) → 7 bits, 280-287 → 8 bits. Distance codes 0-31 all → 5 bits (2531-2532).
- **Length/distance extra-bits tables** `ufbxi_deflate_length_lut[32]` (1854-1859) and `ufbxi_deflate_dist_lut[32]` (1860-1865): pre-generated by `misc/deflate_lut.py` (referenced but not present in this file — external generator script), packed as `[0:5] extra_bits | [5:8] flags | [16:32] base_value`. These encode the standard RFC 1951 Appendix tables (length base 3..258 with 0-5 extra bits across indices 257-285 within `lit_length` symbols 257-287 minus the +256 offset baked into `sym_extra_offset`=256 when building lit_length; distance base 1..24577+ across indices 0-29 with 0-13 extra bits). Do not hand-transcribe — port by regenerating from RFC 1951 tables directly or reading these two arrays as ground truth.
- **Code-length alphabet permutation** `ufbxi_deflate_code_length_permutation[19]` (1867-1869): the fixed RFC 1951 order `16,17,18,0,8,7,9,6,10,5,11,4,12,3,13,2,14,1,15` in which the 3-bit code-length-code lengths are transmitted for dynamic blocks.
- **Dynamic block header fields**: `HLIT` = `bits[0:5]`, real count = `HLIT+257` (257..288); `HDIST` = `bits[5:10]`, real count = `HDIST+1` (1..32); `HCLEN` = `bits[10:14]`, real count = `HCLEN+4` (4..19). Then `HCLEN` triplets of 3-bit code-length-code lengths, then the combined code-length-encoded stream for `HLIT+HDIST` symbols using instructions 0-18 (see algorithm section above for exact repeat semantics/extra-bit counts).
- **`fast_bits`** is either 8 or 10 in normal operation (`UFBXI_HUFF_FAST_BITS`=10 is the compiled-in constant used by the ultra-fast path; plain 8 is chosen automatically for small inputs, `total_size<=2048`, 3146, presumably because building/using a 1024-entry table isn't worth it for tiny data). `internal_fast_bits` may force 1-8 or 10 but **not 9** (rejected with -29) — static assert at 2906-2907 explains why: `UFBXI_HUFF_FAST_BITS<=11` is required so that "fast lit + fast len extra + slow dist" fits in 56 buffered bits, and `fast_bits+UFBXI_HUFF_MAX_LONG_BITS(5) >= 15` is required so the 15-bit DEFLATE max code length is always covered by fast+long combined — 9+5=14 fails that second invariant, only 10+5=15 (or 8 as the "small/slow" alternative, which doesn't need the invariant since it always uses the generic slow decoder pairing) work.
- **Adler-32 trailer**: 4 bytes, big-endian, immediately following the final block's data (after byte-alignment), verified unless `no_checksum`.
- **Error code catalogue**: fully enumerated in the comment block at 3104-3130 (-1 through -30, with some gaps/deprecated codes) — port this 1:1 as a Swift `enum InflateError: Error` with matching cases/associated raw values for parity/debugging, though a Swift API would likely just throw typed errors rather than return negative counts.

## Quirks & edge cases
- **Deterministic float parsing exists specifically to avoid locale bugs**: standard `strtod` is locale-sensitive (some locales use `,` as decimal separator) and its rounding/edge-case behavior varies by libc. ufbx's version is self-contained, always uses `.` as separator, and implements correct round-to-nearest-even via exact bigint arithmetic — critical for exact reproducibility across platforms. The fast path is only enabled after runtime-verifying the compiler's FP unit actually rounds to nearest (`ufbxi_parse_double_init_flags`, 1795-1805) — guards against x87 80-bit extended precision or non-IEEE FP eval modes silently breaking the assumption of exact double arithmetic (relevant historically for 32-bit x86 without SSE2).
- **Legacy MSVC NaN/Inf text forms**: `1.#INF`, `1.#IND`, `1.#NAN` (and variants) are recognized (1554-1568) because older MSVC `printf`/binary FBX exporters from Windows tools emit these instead of standard `inf`/`nan` — a real-world exporter workaround.
- **`nan(...)` payload is parsed but discarded** — any alnum payload in parens is skipped (1574-1585) without affecting the produced NaN bits (matches C99 semantics loosely, but ufbx doesn't encode the payload).
- **Excess digits beyond 14 accumulated limb-groups (~252 decimal digits) are dropped, not stored**, only shifting the exponent (1631-1633) — correct because no valid double distinguishes between values differing only past its ~17 significant digits, but this is a "trust the math" case worth a unit test with pathological many-zero/nine literals.
- **The "small-value shortcut" for negative exponents** (1717-1730) is a targeted optimization for the extremely common case of "modest number of digits, modest negative exponent" (e.g. ordinary vertex coordinates like `1.234567`) skipping the general Knuth division entirely — must be ported faithfully bit-for-bit (including the `-1` in `mantissa_zeros = ufbxi_lzcnt64(digits) - 1`, which assumes `digits` has its own implicit leading 1 already accounted for by construction) or numeric results will silently differ in the last bit for a large fraction of real files.
- **Cancellation protocol** (`ufbx_progress_cb` returning `UFBX_PROGRESS_CANCEL`): `ufbxi_bit_yield` (2154-2164) redirects the stream to a zeroed local buffer and sets `s->cancelled=true`; then every `ufbxi_bit_refill` call checks `dc.stream.cancelled` and forces `*p_bits = s->cancel_bits` (2184-2185, note: `cancel_bits` is declared but its assignment site is not in this span — worth checking the surrounding struct-init code, likely 0, to force a spurious end-of-block/error symbol so decode loops terminate promptly without extra branches). All callers thread a `cancelled` check through and return -28 uniformly. **Not in v1 scope** per the port guidance below (no progress callbacks/cancellation in the Swift port) but the *mechanism* explains a few otherwise-mysterious branches in the hot loops — safe to elide entirely in the port.
- **Overlapping matches with distance < 16 fall back to byte-by-byte copy** (2887-2891, 3065-3078) — required for correctness since DEFLATE explicitly allows distance < length (e.g. RLE-style single-byte run-length matches with distance=1), where a wide SIMD/word copy would read stale (not-yet-written) bytes if done blindly; the `min_dist = length<16 ? length : 16` plus `distance >= min_dist` check exists precisely to detect and avoid that hazard while still using the fast 16-byte path whenever safe.
- **The fast inflate loop never itself reports "ran out of space" as a hard error** for length/distance overflow inline in the middle of decoding two speculative symbols — it computes `dst_space`/`src_space` as signed `ptrdiff_t` and only checks after decoding, returning -12 if either went negative (3052-3056), relying on the fact both quantities were computed from *already fully decoded* symbol values, not out of caution mid-decode.
- **Single-symbol Huffman trees** (only one nonzero-length code in the whole alphabet — legal per RFC 1951, e.g. an all-literal-same-byte block): handled as a special case throughout `ufbxi_huff_build_imp` (`nonzero_sym_count<=1`, 2335-2337, 2354-2358) — canonically assigned a single 1-bit code, and the entire `fast_sym[]` table must be pre-filled with `UFBXI_HUFF_ERROR_SYM` first since the normal "tree is full" fast-table-fill invariant doesn't apply.
- **Static Huffman trees are cross-call cached** in the opaque `ufbx_inflate_retain` (2028, 3211-3216) — if the caller reuses the same `retain` across many `ufbx_inflate` calls (as ufbx's own FBX loader does for every compressed array in a file), the fixed-code tables are built only once total. Must design the Swift equivalent to allow (but not require) reuse of this cache across multiple inflate calls within one document load for a meaningful perf win, or accept rebuilding it every call if `internal_fast_bits` differs (guarded by the `input` param passed to `ufbxi_init_static_huff`, 2510-2520 — note a *fixed* fast_bits override could in principle be baked wrong into a stale cached retain-buffer if `internal_fast_bits` changes between calls sharing one `retain`; ufbx assumes callers don't do that).
- **`internal_fast_bits` validity is checked twice** — once informally in comments ("must always be valid as checked in the beginning of `ufbx_inflate`") and once for real (3141-3147) before the static-huff init path (2515-2517, which only asserts, doesn't re-validate) — so the *public* entry point is the sole enforcement point; a Swift port exposing only the safe path can drop the internal-fast-bits knob entirely (it's explicitly a profiling/debug knob per the `// TODO: Profile this` comment at 3145).
- **Regression-only assertions** (`#if defined(UFBX_REGRESSION)` blocks, e.g. 2271-2283, 2437-2450) are expensive exhaustive fill-checks meant for ufbx's own test suite, not production — skip porting these as runtime code; consider Swift unit tests that assert the same invariants once against fixture data instead.

## Port guidance
- **Float parsing**: Port `ufbxi_parse_double` faithfully at the bit level — this is exactly the kind of "must match reference C behavior precisely" logic the porting effort should not re-derive. Recommended Swift shape: a free function `parseFBXDouble(_ bytes: some Collection<UInt8>) -> (value: Double, consumed: Int)` (or operating on `Substring`/`UnsafeBufferPointer<UInt8>`) mirroring the C signature (`str`, `max_length`, out `end`). The bigint arithmetic (`ufbxi_bigint_mad`, `_div`, `_mul_pow5`, `_shift_left`, `_extract_high`) should be ported as a small private fixed-capacity `[UInt32]`-backed struct (Swift arrays are fine here, or a tuple/inline-array for zero-alloc if performance matters — but note this isn't hot enough during scene load to need SIMD, unlike inflate). Consider whether Swift's own `Double(String)` / a Swift decimal parser is "close enough" — it likely is NOT, because ufbx's is exactly reproducible and handles the MSVC legacy NaN/Inf spellings that real exported FBX-ASCII files contain (a stretch-scope decision: at minimum keep `ufbxi_parse_inf_nan`'s special forms even if the numeric bigint path is eventually replaced by Swift's native parser, since Double("1.#IND") will simply fail in Swift). Given the port scope explicitly lists "custom string-to-double parser" as in-scope, port it whole.
- **`ufbxi_parse_int64`/`ufbxi_parse_uint32_radix`**: trivial — replace with ordinary Swift integer-parsing (`Int64(String)`, manual radix loop, or `strtoul`-equivalent), no need to port the exact C logic; these aren't precision-sensitive.
- **Inflate — port faithfully**: the Huffman table construction, block-type dispatch, dynamic-header decode, canonical-code math, and length/distance extra-bit tables must be ported exactly (per scope: "pure Swift port of ufbx_inflate"). This is the single most algorithmically dense piece of C in the whole file; budget real time for it.
- **Inflate — replace with Swift idioms**:
  - Drop the streaming `read_fn`/`buffer`/multi-chunk plumbing (`ufbxi_bit_stream_init`, `_chunk_refill`, `_yield`, progress callbacks, cancellation) entirely — v1 scope note says "Swift uses Data/URL" and "progress callbacks" are explicitly OUT of scope. Operate on a single in-memory `Data`/`[UInt8]` buffer for both binary-FBX compressed arrays (already whole in memory) and no streaming decompression is needed. This eliminates most of `ufbxi_bit_stream`'s fields, `ufbxi_bit_chunk_refill`, `ufbxi_bit_yield`, and the cancellation branches sprinkled through the hot loops — a huge simplification.
  - Still port the **branchless 64-bit bit-refill trick** (`ufbxi_bit_refill`/`ufbxi_macro_bit_refill_fast`) since it's central to inflate's speed and translates cleanly to Swift (`UnsafeRawBufferPointer.loadUnaligned(as: UInt64.self)` + shifts), but it can be simplified to always read from one contiguous buffer with a simple end-of-buffer zero-pad copy (mirroring what `ufbxi_bit_chunk_refill`'s zero-pad-to-64 does) rather than the multi-chunk state machine.
  - The dual fast/slow decode-loop split (`ufbxi_inflate_block_fast` vs `_slow`) is worth preserving as an optimization if Swift performance requires it, but consider first shipping just the slow/general path (`ufbxi_inflate_block_slow`'s algorithm, ported straightforwardly) and only adding the SIMD-adjacent fast-path duplication if profiling shows it's needed — Swift's optimizer and the removal of the streaming abstraction may make the simpler path fast enough, unlike C where every function call has real overhead.
  - `ufbxi_adler32`: drop the hand-written SSE2 branch; keep (or write fresh) the simple scalar/64-bit-word version — correctness-critical (must exactly match zlib's Adler-32) but not `ufbx`'s specific vectorization. Alternatively use `zlib`'s `adler32` via a system import if the "zero dependencies" constraint permits linking libz for just a checksum — but given "zero dependencies" is stated as a hard target, port the algorithm (not the SIMD).
  - The `retain`/cache-static-trees mechanism can become a lazily-initialized `static let` (or a `struct DeflateStaticTrees` built once and reused) rather than an opaque caller-provided byte buffer — Swift has no ABI reason to keep the C "retain" blob shape.
  - Bit-reversal (`ufbxi_bit_reverse`), Huffman symbol packing (`ufbxi_huff_sym`) and the fast/long/sorted three-tier table design should be ported as-is (as Swift structs/`UInt16`s with the same bit layout, or unpacked into cleaner Swift enums with associated values if profiling shows no cost — but the packed-integer scheme exists purely for speed, and a first Swift port might reasonably use a plain-old `enum HuffSymbol { case literal(UInt8); case match(lengthIndex: Int); case endOfBlock; case invalid }` for clarity, falling back to the packed representation only if it becomes a bottleneck).
- **Dependencies / what feeds what**: `ufbx_inflate` is called by the **binary FBX parser** (outside this span) whenever a property's array is flagged as zlib-compressed (binary FBX encoding byte for arrays: 0=raw, 1=zlib — the calling code lives elsewhere in ufbx.c and is a different subsystem's territory, but it is the sole consumer here). `ufbxi_parse_double`/`_parse_int64`/`_parse_uint32_radix` are called by the **ASCII FBX tokenizer/parser** (also outside this span) to convert `NUMBER` tokens into `ufbx_real`/int property values, and transitively feed every downstream scene-construction subsystem (meshes, transforms, animation curves — anything with a floating-point value in an ASCII file depends on this parser being bit-exact). No subsystem in this span depends on anything outside it — this is a leaf/foundation module and should be ported and unit-tested first, independent of the rest of the parser.
- **Suggested error handling shape**: replace the C `ptrdiff_t` (byte-count-or-negative-error-code) return convention with a throwing Swift function returning the decompressed `Data`/byte count, e.g. `func inflate(_ input: Data, expectedSize: Int) throws -> Data`, with a Swift `enum InflateError: Error { case badZlibHeader, badBlockType, checksumMismatch, ... }` mapped 1:1 from the documented codes (3104-3130) for debuggability, dropping codes that only exist for the streaming/cancellation machinery being removed (-28 Cancelled, -29 internal_fast_bits, and the deprecated -8).
